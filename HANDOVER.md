# 🌳 «Род» — семейное древо

**Версия:** 2.1.0 · **Обновлено:** 29 октября 2026 · **Статус:** рабочее приложение; сервер и чистая логика — 40 тестов, интерфейс — 31 сквозной шаг в реальном Chromium (все зелёные).

Одностраничное приложение для ведения семейных древ: вход по логину, совместное редактирование в реальном времени, история версий с авторством и откатом, фото в исходном качестве, биографии, экспорт в архив с готовым хранилищем Obsidian, работа офлайн (PWA).

---

## 1. Быстрый старт

Нужен **Node.js 22.13+** (используется встроенный `node:sqlite`).

```bash
npm install          # ws (обязательно), sharp (по желанию — миниатюры фото)
npm start            # http://localhost:3000
npm test             # серверные и чистые тесты (≈ 5 с)
npm run e2e          # браузерные тесты (нужен: npx playwright install chromium)
```

Docker: `docker build -t rod . && docker run -p 3000:3000 -v rod-data:/data rod`.

Все настройки — переменные окружения, см. `.env.example` (`node --env-file=.env server.js`).
**За HTTPS-прокси** обязательно `TRUST_PROXY=1` (тогда cookie получает `Secure`, берётся реальный IP для лимитов).

### Переход со старой версии (1.0)
Положите старые `data/users.json`, `trees.json`, `history-*.json`, `sessions.json` в `DATA_DIR` и запустите — при первом старте всё переедет в SQLite автоматически:
пароли остаются рабочими, сессии живы, история из полных снимков превращается в компактные диффы, «место» из начала биографии (`[Тверь]\n…`) выносится в поле «Место рождения», односторонние связи супругов достраиваются. Старые файлы переименовываются в `*.migrated` (не удаляются).

## 2. Что реализовано

**Аккаунты и безопасность**
- Регистрация/вход (scrypt), смена пароля (остальные устройства разлогиниваются), сессии 30 дней в `HttpOnly` cookie; токены в БД хранятся **только в виде SHA-256**.
- Защита от CSRF (обязательный заголовок `X-Rod` + проверка `Origin`), проверка `Origin` у WebSocket, CSP без inline-скриптов, ограничение попыток входа (по IP и по паре IP+логин), лимит регистраций и общий лимит запросов.
- Серверная валидация всех полей (длины, формат дат, id, URL фото только из своего древа), отказ при циклах родства и при попытке сделать предка/потомка супругом или братом/сестрой; фото проверяются по содержимому (magic bytes), а не по заголовку.
- Права: владелец и приглашённые; удалять древо и управлять доступом — только владелец.

**Данные участника:** имя, девичья фамилия, пол, даты рождения/смерти, место рождения и смерти/захоронения, школа, профессиональное образование, профессия, место работы, биография, фото (оригинал без сжатия), связи: родители, супруги, братья/сёстры (+ производные по общим родителям). Все связи двусторонние и **удаляются так же симметрично**, как добавляются.

**Древо:** раскладка по поколениям (дети под парой, цепочки браков, корректно при «супруге без родителей»), линия рода подсвечивается, линейка поколений с десятилетиями, мини-карта, жесты (панорама, колесо к курсору, щипок), отсечение невидимых карточек (600 человек ≈ 150 карточек в DOM, ~60 кадров/с), траурный уголок, возраст, быстрые кнопки «＋ Родитель / Супруг(а) / Ребёнок / Брат-сестра», поиск с опечатками, статистика и ближайшие даты, тёмная тема, мобильная версия (нижний лист, боковая панель).

**Совместная работа:** WebSocket с патчами (а не целым древом), присутствие, пинги и автопереподключение с догрузкой. Слияние **на уровне карточки**: правки разных людей не конфликтуют; при конфликте одной карточки пользователь видит «Загрузить актуальную / Сохранить поверх», введённое не теряется.

**История:** каждая правка — запись с автором, временем и перечнем затронутых людей (хранятся диффы, до `HISTORY_LIMIT`=1000 ревизий). Откат создаёт **новую** ревизию, историю не стирает; откат возможен «вперёд» и «назад».

**Экспорт/импорт:** ZIP (`tree.json`, `tree.html` — офлайн-страница с картой древа и биографиями, `Obsidian/` — готовый vault с `[[ссылками]]` на родителей, супругов, братьев/сестёр и детей, фото в `Obsidian/media/` в оригинале). Импорт принимает такой ZIP или чистый JSON и создаёт **новое** древо. SVG-плакат для печати.

**Облако (S3-совместимое):** постоянная очередь (`outbox` в БД) с повторами и нарастающей паузой: версии, «голова» древа, фото (с правильным Content-Type), ежесуточная согласованная копия всей БД.

**PWA:** оболочка работает без сети; офлайн открывается последняя копия древа **только для просмотра**.

## 2а. Что нового в 2.1

- **Девичья фамилия** (поле у каждого; видна на карточке, в профиле, в поиске, в экспорте Obsidian — `maiden_name` и алиас).
- **Годовщина свадьбы:** дата хранится у обоих супругов и зеркалится (правка у одного видна у другого, очистка/развод/удаление супруга чистят у обоих). В профиле — «N лет вместе» (или «в браке» до смерти одного из супругов) и юбилей («серебряная», «золотая»…), год подписан на линии брака, ближайшие годовщины — в «Статистике», даты есть в Obsidian и `tree.html`.
- **Направление «снизу вверх»** (по умолчанию): потомки выше предков. Переключается в меню «⋯» → «Потомки снизу (классика)»; настройка запоминается на устройстве.
- **Раскладка родных:** дети одного брака стоят рядом от старшего к младшему, дети от разных браков — отдельными блоками; супруг(а) первого в группе — слева, остальных — справа (снаружи). Шины разных семей одного родителя разнесены по уровням, порядок подбирается перебором так, чтобы линии не пересекались; явные «брат/сестра» без общих родителей соединены пунктиром. Корректность линий проверяется геометрически (пересечения, наложения шин, проход сквозь чужие карточки) — см. `test/pure.test.js`.
- **Поколения (ряды):** на одном ряду стоят супруги, явные «брат/сестра» и все дети общего родителя (в т.ч. единокровные). Предки без записанных родителей подтягиваются вплотную над своими детьми, а не прижимаются к верхнему краю, так ровесники из разных ветвей оказываются в одном ряду. Шины семей, перекрывающиеся по ширине в одной полосе, разнесены по уровням — даже если родители разные.
- **Подсветка семей** (меню «⋯» → «Подсветить семью или фамилию…», кнопка «Подсветить семью» в профиле): либо все люди с выбранной фамилией (по желанию — и женщины, для которых она девичья), либо одна семья: своя (человек, супруги, дети), родительская (родители и все их дети) или вся ветвь. Остальные карточки и линии приглушаются, линии между подсвеченными — золотые; плашка вверху показывает, что включено, крестик снимает. Подсветка постоянная: не сбивается наведением мыши, переживает правки и смену раскладки, сбрасывается при смене древа. Фамилия определяется эвристикой (`public/js/family.js`): мужские и женские формы считаются одной фамилией, порядок слов («Имя Фамилия» или «Фамилия Имя») определяется по большинству записей древа; отдельного поля «фамилия» в данных нет. Для имён, которые эвристика принимает за фамилию (или наоборот), правильное решение — поле в карточке, это в планах.
- **Где данные и версии.** Всё в папке `data/` рядом с `server.js` (или `DATA_DIR`): `rod.db` — база SQLite (люди, аккаунты, история правок, очередь облака), `media/<id древа>/` — оригиналы фото, `thumbs/` — миниатюры (пересоздаются). **Файловые копии:** после КАЖДОЙ правки сохраняется отдельный файл `versions/<id древа>/r000042_20261031-154747_логин.json` (полное состояние древа в формате `tree.json`; последние 300 хранятся все, старше — по одной на день до 120 дней), раз в сутки — копия базы `versions/db/rod-ГГГГММДД.db` (14 штук). Настройки: `ROD_SNAPSHOTS=0` (выключить), `ROD_BACKUP_DIR` (куда писать, например общий раздел телефона), `ROD_SNAPSHOT_KEEP`, `ROD_SNAPSHOT_DAYS`, `ROD_DB_BACKUPS`. Откат: интерфейс («История») либо, если база повреждена/потеряна, `node tools/restore.mjs list|apply <файл>|db <копия.db>` (при остановленном сервере). Откат не стирает историю и сам сохраняется файлом. **Ручная полная копия** одним ZIP (база со всеми древами, аккаунтами и историей, все фото, файлы версий): `npm run backup` (можно при работающем сервере; папка по умолчанию `~/storage/shared/RodBackups`, иначе `--out`), восстановление — `node tools/restore.mjs full <rod-backup-….zip>` (сервер остановить; прежняя `data` сохраняется как `data.before-restore-…`). **Из приложения:** меню «⋯» → «Полная копия всех данных (ZIP)…» (тот же файл, что даёт `npm run backup`; пункт видит только владелец сервера — логины из `ROD_ADMINS`, иначе первый зарегистрированный аккаунт; остальным `/api/admin/backup` отвечает 403, потому что в копии аккаунты и хеши паролей всех пользователей; за раз готовится одна копия). Восстановление из приложения не реализовано — только `restore.mjs full`. Кнопка «Скачать архив» в приложении — отдельная копия ОДНОГО древа (с Obsidian), она восстанавливается через «Импорт» как новое древо. Фото в версии не копируются (лежат в `media/` и не удаляются, пока цело древо); при удалении древа файлы `versions/` остаются намеренно.
- **Родственники из других домов.** Регистрация по умолчанию только по приглашению (`ROD_REGISTRATION=invite|open|closed`; самый первый аккаунт создаётся всегда). Владелец древа: «Пригласить по ссылке…» (срок 1–30 дней, 1–20 человек, пометка «для кого», отзыв); ссылка `…/?invite=ТОКЕН` одноразовая по числу людей, в базе хранится только sha256 токена (таблица `invites`), токен после открытия убирается из адресной строки; зарегистрировавшийся по ней получает доступ к древу (соавтор: правит, но не приглашает и не удаляет древо). Уже зарегистрированный принимает ссылку через `/api/invite/accept`; повторное открытие — «вы уже в древе»; занятый логин ссылку не сжигает. `PUBLIC_URL` подставляется в окно приглашений, `TRUST_PROXY=1` — за туннелем/прокси. Как выставить сервер в интернет (Cloudflare Tunnel с телефона, VPS + Docker + Caddy, Tailscale) — `ДОСТУП-ИЗ-ИНТЕРНЕТА.md`; сами туннели и хостинг в разработке не проверялись (нет интернета).
- **Android.** Основной путь — установка как PWA (`АНДРОИД.md`): манифест полный (иконки any/maskable, `id`, скриншоты narrow/wide, `display_override`), проверка установки и доступности всех ресурсов манифеста — в e2e. APK из HTTPS-адреса — через PWABuilder (TWA); для режима без адресной строки сервер отдаёт `/.well-known/assetlinks.json` из файла `data/assetlinks.json`. Оболочка Capacitor (`android/`) теперь спрашивает адрес сервера при первом запуске (раньше был прописан `127.0.0.1`), но **не собиралась**, а скачивание файлов в WebView не работает.
- **Контакты в карточке:** телефон (несколько через запятую), e-mail (один или несколько), адрес проживания (текущий/последний). В профиле телефон и e-mail — ссылки (`tel:`, `mailto:`), поиск находит по e-mail, номеру (от 6 цифр) и адресу; попадают в Obsidian (frontmatter `phone/email/address` + текст) и `tree.html`, **не** попадают в SVG-плакат. Проверка на сервере: e-mail по формату, телефон — цифры и допустимые знаки; при импорте мусор отбрасывается. **Приватность:** контакты видят все, у кого есть доступ к древу (в т. ч. приглашённые родственники) и все, кому вы передадите экспорт/полную копию.
- **Вложенные документы:** у карточки до 40 файлов — PDF (до 25 МБ, `MAX_DOC_MB`) и фото (без пережатия, до 40 МБ; HEIC/AVIF/GIF браузер переводит в JPEG). Поля: название, вид (свидетельство о рождении/браке/смерти, метрика, диплом, паспорт, военный билет, письмо, другое; вид угадывается по имени файла), исходное имя, размер. Хранение: `data/media/<древо>/<uuid>.pdf|jpg|png|webp`, в карточке — список `docs` (поэтому они есть в истории, откате, синхронизации, слиянии дублей). Загрузка `POST /api/trees/:id/doc` (тип файла определяется по содержимому, а не по имени; доступ — только участникам древа). Файлы НЕ удаляются при удалении из карточки (нужны истории), только вместе с древом. Идут в «Полную копию», экспорт (Obsidian: раздел «Документы» со ссылками, файлы в `Obsidian/media/`; `tree.html`) и импорт (переезжают в новое древо), поиск по названию/виду. Приватность та же, что у контактов: видят все участники древа.
- **Компактность семей (раскладка).** Пара «ведётся» по линии отца (меню «⋯» → «Вести пары по линии матери»): родители мужа — это дерево, к которому пара относится, поэтому люди с одной фамилией (родители, брат/сестра, дети) собираются в один блок. Независимые «деревья» (например, предки мужа, пришедшего в семью со стороны) больше не выстраиваются слева направо по порядку создания: каждое ставится как можно ближе к тем, с кем связано (выравнивание по якорям связей), а при нехватке места — над свободными местами соседнего ряда (контурная упаковка, `layout.js`: `walk`/`trees`/`links`). Измерено на реальном древе (46 человек, выгрузка пользователя): разброс по горизонтали для Никитченко 3648 → 720 px, Мартыненко 1680 → 960 px, суммарная длина связей ребёнок↔родители −27%; на проверочном древе (`test/compact.test.js`) −41%, самая длинная связь −63%. Остаётся неизбежное: человек, вышедший замуж/женившийся из другого блока, связан с родителями длинной линией.
- **Шкала по годам (эксперимент):** меню «⋯» → «Шкала по годам». Вертикальное положение пропорционально году рождения (8 px/год), слева линейка десятилетий, на холсте пунктирная сетка. Если года нет — он оценивается по супругу, братьям/сёстрам, родителям (+28), детям (−28); такие карточки обведены пунктиром. Положение карточек, оказавшихся рядом по году и по горизонтали, слегка корректируется, чтобы не накладываться.
- **Дубли:** выбор связей переписан (идемпотентное добавление, список не зависит от фокуса — на сенсорных экранах прежняя схема была ненадёжной); при создании тёзки показывается предупреждение; «Объединить с…» в профиле переносит связи, детей, даты и пустые поля, удаляет лишнюю карточку одной атомарной правкой (её можно откатить из истории).
- **Фото из Google Фото:** на телефоне системный выбор файла показывает «Google Фото», поэтому выбрать оттуда можно уже сейчас; форматы вне JPG/PNG/WebP (HEIC, AVIF, GIF…) браузер преобразует в JPEG 95%. **Прямая интеграция с Google Photos (Picker API) не сделана:** требует OAuth-клиента в Google Cloud и интернета, проверить без них нельзя.
- **Приложения:** PWA устанавливается на Android и в Windows (Chrome/Edge): Chrome DevTools сообщает 0 ошибок установки, в меню есть «Установить приложение». Исходники нативных оболочек — `desktop/` (Electron, Windows) и `android/` (Capacitor, APK) и сборка на GitHub Actions: **не собирались** (нет Windows/Android SDK/сети); для Electron проверен только запуск встроенного сервера (`desktop/smoke.mjs`).

## 3. Архитектура

```
server.js            HTTP API, WebSocket, статика, фото, экспорт/импорт, wiring
lib/store.js         SQLite (node:sqlite): пользователи, сессии, древа, люди, история, outbox
lib/tree.js          чистая логика: applyOps (слияние, связи, циклы), диффы, откат
lib/validate.js      валидация и очистка данных
lib/migrate.js       миграция со старого JSON-формата
lib/cloud.js         S3: подпись SigV4 + очередь выгрузки + бэкап БД
lib/export.js        Obsidian-vault, tree.json, офлайн-страница
lib/zip.js           ZIP-писатель/читатель без зависимостей
public/js/layout.js  алгоритм раскладки (общий для браузера и сервера)
public/js/util.js    даты, возраст, поиск (чистые функции)
public/js/stats.js   статистика и ближайшие даты
public/js/svg.js     SVG-рендер (плакат и офлайн-страница)
public/js/app.js     весь интерфейс
public/sw.js         сервис-воркер
test/*.test.js       node --test
tools/e2e.mjs        сквозные тесты в Chromium
desktop/             Electron-оболочка для Windows (не собиралась)
android/             Capacitor-оболочка для APK (не собиралась)
```

**Модель правок.** Клиент шлёт `POST /api/trees/:id/save` с `ops: [{op:'put', person, base}, {op:'del', id, base}]`, где `base` — ревизия карточки (`r`), которую он видел. Сервер атомарно применяет пачку, нормализует связи, и если `base` устарел — отвечает `409 {conflicts:[id…]}`, ничего не записав. Если в одной пачке правятся обе стороны связи — побеждает более поздняя операция.

**API** (все изменяющие запросы требуют заголовок `X-Rod: 1`):

| Метод и путь | Назначение |
|---|---|
| `POST /api/register`, `/api/login`, `/api/logout`, `/api/password` | аккаунт |
| `GET /api/me` | пользователь и список древ |
| `POST /api/trees` `{name, sample?}` · `POST /api/trees/import?name=` (тело — ZIP/JSON) | создать / импортировать |

## 4. Чего нет и ограничения (честно)

- **Не сделано из прежнего roadmap:** гео-карта миграций (нужны тайлы карты — внешний сервис), OCR документов, e-mail/push-уведомления (нужен почтовый сервис), PostgreSQL (вместо него SQLite — один файл, WAL; хватает на тысячи пользователей на одном сервере, но это **один процесс**: горизонтально не масштабируется), расширенные типы связей (приёмные дети, даты браков, разводы).
- **Облако проверено без реального S3:** подпись сверена с двумя эталонными векторами из документации AWS, выгрузка/повторы/бэкап — на локальном mock-S3. На вашем провайдере проверьте `/healthz` → `cloud.queue` (должна стремиться к 0). Чтение из облака (восстановление) вручную: объекты `trees/<id>/head.json` содержат полное древо.
- ZIP без ZIP64 (архив < 4 ГБ); импорт читает архив в память (лимит `MAX_IMPORT_MB`).
- Фото, загруженные, но не сохранённые в карточке, остаются на диске (уборщика «сирот» нет).
- Раскладка: если у человека родители из двух разных семей (супруг со стороны со своими родителями), линии к ним могут пересекаться; порядок корней — по порядку создания. Если у трёх и более родных есть супруги, супруги средних стоят между братьями/сёстрами — строго «снаружи» можно только у крайних.
- Режим «по годам» экспериментальный: на очень плотных древах карточки могут сдвигаться относительно точного года, чтобы не налезать друг на друга.
- Приглашённые видят изменения в реальном времени внутри древа, но новое приглашение в список древ подтягивается при возврате на вкладку.
- `Dockerfile` и CI-конфиг написаны, но не запускались (в среде разработки нет Docker/GitHub) — проверьте первую сборку.
- Нет `package-lock.json` (создан без доступа к сети) — выполните `npm install` и закоммитьте его.
- Node 22.13+ печатает предупреждение «SQLite is an experimental feature» — это нормально.
